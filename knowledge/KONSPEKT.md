# SkyWorker — Реестр операторов дронов. Конспект проекта

_Обновлено: 2026-09-03. Ведёт: Руслан (по договорённости с Нурланом, владелец SkyWorker)._

## 1. Что за проект
Реестр (маркетплейс) операторов дронов для Казахстана — «Naimi.kz только для дронов».
Две стороны:
- **Операторы** — регистрируются сами, кладут профиль, допуски, навыки, оборудование, портфолио.
- **Заказчики** (компании/предприниматели) — ищут и нанимают операторов.

Модуль войдёт в существующую платформу **SkyWorker ERP** как раздел «Consumer → Кадры → Оператор».
Руслан ведёт этот блок отдельно, потом врезаем в общую платформу.

## 2. Кто такие SkyWorker (по факту)
- Официальный **дистрибьютор DJI Agriculture** в Казахстане. Профиль — **агродроны** (Agras T100/70/55, Mavic 3M).
- Instagram @skyworker.kz: 9 579 подписчиков, 385 постов, бизнес-аккаунт. Контент весь агро (десикация, обработка полей, тесты).
- Есть **Центр компетенций БПЛА** на базе QAIRU + магистратура по беспилотным системам — сами готовят операторов и выдают допуски.
- Работают с **CAA.gov.kz** — госрегистрация агродронов, официальные допуски.
- Дилерская сеть: **13 дилеров** (авторизованные партнёры-реселлеры) по городам. Нурлан для них — дистрибьютор.

## 3. Разбор их платформы app.skyworker.kz (разведка 2026-09-03)
- Название внутри: **«SkyWorker ERP»**.
- **Фронт:** React + Vite (SPA). **Бэк:** похоже FastAPI (Python). Веб: nginx за Caddy.
- **API:** REST по `/api/v1`, есть `/api/health`. Авторизация — **JWT** (access+refresh, HS256).
  Логин: `POST /api/v1/auth/login {email, password}` → `{data:{access_token, refresh_token}}`.
  OpenAPI-доки в проде закрыты. Ответы обёрнуты в `{data: ...}`.
- Доступ (дал Нурлан): admin@skyworker.kz. Разработку ведут активно (обновляли 02.09.2026).

**Что в платформе УЖЕ есть (52 страницы-раздела):**
- Склад/остатки: Warehouse, StockAndReserves, Batches
- Запчасти/логистика: PartOrders, DonorRequests, Shipments, IncomingReview
- Сервисные заявки клиентов: Requests (List/Kanban/Table/Detail) — то, что в инсте
- Каталог + **интеграция с 1С**: OneCCatalog, OneCStock
- Справочники: **Organizations** (дилеры), **Regions** (регионы), **Users**, задачи, аналитика, CommandCenter
- Auth: Login/Register/Forgot/Reset

**Чего в платформе НЕТ:** ни одной страницы про операторов — ни реестра, ни портфолио, ни навыков, ни допусков, ни рейтингов. **Блок «Оператор» они не начинали — поле чистое, целиком наше.** Мы НЕ пересекаемся с тем, что их команда пилит сейчас (запчасти/склад/1С).

**К чему стыкуемся:** Users (единый вход/JWT), Organizations (кто нанимает), Regions (регион оператора).

## 4. Решения по проекту (согласовано с Русланом)
1. **Монетизации на старте НЕТ.** Главная ценность = **база контактов** операторов и заказчиков. Деньги — потом.
2. Из п.1 следствие: приоритет — **лёгкая self-service регистрация** обеих сторон (иначе базу не набрать) и **согласие на обработку ПД + маркетинг** с первого дня (потом этой базе будем что-то предлагать → согласие обязательно по закону РК).
3. **Не только агро.** Цель — весь рынок дронов. Старт с агро (актуально), архитектура — широкая. «Направление» = **расширяемый справочник**, новая отрасль = одна запись. НО: детально прорабатываем ПОКА только агро; остальные направления просто заложены структурно, не расписываем — вернёмся к ним, когда будет готов интерфейс по агро (решение Руслана: «не бежать вперёд коней»).
4. **Услуги закладываем сразу одним блоком** с реестром (решение Руслана). Не разделять — потом разделять сложно. Один профиль оператора с типом (наёмный / услуги со своим оборудованием / оба).
5. Категории допусков I/II/III и классификацию обучения — **не гадаем, запрос Нурлану** отдельным письмом.
6. Владелец аккаунта / модель прав — пока открыто, цель: ценность для обеих сторон.
7. **Стартовое наполнение — 2-3 выдуманных демо-профиля оператора**, которые заведём сами для наглядности/видения. Реальные операторы на старте НЕ нужны (решение Руслана). Нурлана этим не грузим.
8. **Архитектура старта (решение Руслана):** MVP делаем как **независимое приложение на своём сервере/железе**, к платформе SkyWorker сейчас НЕ подключаемся, API-ключи от них не берём. Стыковка — потом (передадим код на вшивку ИЛИ настроим обмен данными). Пишем на их же стеке (см. раздел 11). «Розетки» = заранее согласованные точки стыковки (по каким id матчатся Users/Organizations/Regions).

## 11. Технический контракт стыковки (подтверждено их разработчиком, 2026-09-03)
**Наш стек фиксируем = их стек (для лёгкой будущей вшивки):**

- Frontend: **React 18.2 + TypeScript 5.3 + Vite 5.1**, React Router 6.22, TanStack Query 5.x
- БД: **PostgreSQL 17** через SQLAlchemy 2.0 + psycopg 3.2

**Идентификация — везде UUID:**
- `users.id`, `organizations.id`, `regions.id` — UUID
- Связи: `users.organization_id`, `users.region_id`, `organizations.region_id`
- Внешние сущности из 1С: `organizations.external_id` + `source_organization_id`

**Рекомендация разработчика (принимаем):**
- Наш реестр — **отдельный сервис с REST API**, не вшивать код напрямую (независимый деплой, не трогаем их ERP, подключим через API позже).
- У наших операторов — **собственный UUID + отдельное поле external_id** для будущего обмена.
- В REST API — ссылки на их пользователей/организации/регионы по UUID.

→ Итог: стыковка технически подтверждена. Проектируем свою БД с полями `external_user_id`, `external_org_id`, `region_id` (UUID) под будущий матчинг.

## 5a. Роли и доступ (модель — разложено 2026-09-03)
**Принцип: аккаунт один, роли совмещаются.** Вход один (телефон/email, один владелец), а «что ты делаешь» — роли, которые включаются в кабинете. Это решает случай «компания и оказывает услуги, и сама ищет операторов».

**Три роли:**
- **Оператор (ищу работу)** — физлицо. Публичная карточка-резюме: портфолио, навыки, допуски. Цель — чтобы наняли в штат/на сезон.
- **Исполнитель услуг** — ИП / мини- или крупная компания со своими дронами (от 1 до 50+). Публичная карточка-витрина услуг: оборудование, услуги, цены, покрытие. Цель — чтобы заказали услугу.
- **Заказчик (нанимаю/ищу)** — публичной карточки НЕТ; пользуется поиском + оставляет заявки.

**Развилка при регистрации** («Что вы хотите?»): найти оператора/услугу · предложить себя как оператор · оказывать услуги. Но роли не взаимоисключающие — исполнитель услуг может включить роль «Заказчик»; в кабинете тогда два раздела: «Моя витрина услуг» + «Мой поиск операторов».

**Каталог (что видит ищущий) — две стороны:** вкладки/фильтр «**Операторы**» (физлица по найму) и «**Услуги**» (компании-исполнители). Заказчик выбирает: человека в штат или подрядчика на услугу.

**Доступ:** просмотр каталога — БЕЗ регистрации (гостём, чтобы приходили и видели ценность). Контакты / «Связаться» / заявка — ТОЛЬКО после регистрации → так собираем данные о заказчике (ценность базы). Решает колебание Руслана «регистрироваться или нет».

**Видимость прайса услуг (обсуждение конкуренции 03.09):** оператор-исполнитель САМ выбирает, как показывать цену — «Открытый прайс» (от N ₸/га + сетка) / «Цена по запросу» / «Договорная». Снимает страх, что все цены на виду и жёсткая конкуренция. Идею собственного внутреннего прайс-калькулятора («наша система прайс») отложили (Руслан: пока не надо).

**Важно про термины:** показанная в прототипе карточка оператора — это ПУБЛИЧНЫЙ профиль-витрина (как его видит заказчик), НЕ личный кабинет. Кабинет — отдельный экран, где владелец редактирует свою карточку.

## 6. Черновая модель данных
**Участник (Оператор):**
- Тип: `наёмный` / `услуги (со своим оборудованием)` / `оба` (один профиль, переключатель)
- ФИО, фото, контакты (тел/WhatsApp/email), город → Regions
- Направления (мультивыбор из справочника)
- Навыки/специализации
- Допуски/сертификаты: категория, кем выдан, срок → статус верификации
- Опыт: стаж, объём работ (га/часы/кейсы)
- Оборудование (если тип «услуги»): модели дронов, количество
- Портфолио: фото/видео/кейсы
- Рейтинг / отзывы
- Условия/ставка (опционально). Модель цены услуг по прайсу JEDI (03.09): НЕ фикс, а `price_from` («от N ₸/га») + опциональная тарифная сетка объём→цена (таблица service_tiers) + флаг «цена договорная». Доп. поля услуги-компании: оборудование (T50/T100), охват/регионы, число бригад, опыт, производительность (га/смена).
- Мед-осмотр / агроном (из схемы 2) — опционально
- Статус доступности: `открыт к предложениям / занят / не беспокоить` + настройка приёма заявок (контроль потока, из обсуждения мотивации оператора). Связь только через платформу, не прямой контакт.
- Образец услуги для демо: ТОО «JEDI» (партнёр SkyWorker, DJI Agras T50/T100, Астана, сетка 100га=5000₸ … 8000га=2700₸).
- **Согласие на обработку ПД + на маркетинговые сообщения** (обязательно)

**Заказчик (Компания):**
- Организация → Organizations, контактное лицо, регион
- Заявка/вакансия: направление, регион, тип (найм / разовая услуга), описание, бюджет, сроки
- Поиск/фильтр операторов (направление + регион + допуск + рейтинг)

## 6a. Профиль оператора — ДЕТАЛЬНО (по документу «Профиль оператора БАС», Жолдузай 03.09)
Их видение полей — глубже моего по агро. Принцип: клиент сразу видит ключевое (не длинная анкета).

**Тип исполнителя (уточняет роли):**
- Оператор со своим БАС · Оператор без собственного БАС (работает на чужой технике/парках) · Владелец парка / компания.
- Важно: оператор БЕЗ своего дрона не должен теряться — его нанимают владельцы парков (внутренний B2B-спрос на платформе).

**Категория оператора (аналогия с правами A/B/C, зависит от веса БАС) — универсальное поле для любого дрона:**
- 1 кат: 250 г–1,5 кг — любительские, фото/видео
- 2 кат: 1,5–25 кг — коммерческие: картография, геодезия, поиск-спас
- 3 кат: 25–750 кг — авиахимработы, грузоперевозки (АГРО = 3 категория!)

**Документы и регистрация (РАЗДЕЛЯТЬ — это разное):**
- Права/свидетельство оператора — есть/нет
- Категория оператора — 1/2/3
- Регистрация БАС — зарегистрирован/нет
- Регистрационный номер БАС (как госномер авто)

**Оборудование (не просто «агродрон»):**
- Модель, на которой работает СЕЙЧАС (напр. DJI Agras T70)
- Модели, на которых работал РАНЬШЕ (T50/T100)
- **Бак-разбрасыватель — есть/нет** (ключевой признак! Стандартный бак = жидкостные обработки; для сыпучих удобрений/семян нужен разбрасыватель. Аналогия «детское кресло в авто»).

**Перевозка/доптехника (для агро):** Автомобиль · Прицеп · Специализированный прицеп · Ёмкость для воды — каждое есть/нет.

**Опыт (детально):** общий опыт с БАС (лет) · опыт с агродронами (лет) · кол-во сезонов · обработано га · модели сейчас/ранее.

**Услуги агро (справочник):** гербицидная / фунгицидная / инсектицидная обработка · десикация · внесение удобрений (жидкие/сыпучие) · подкормки · разбрасывание семян.

**Шаблон карточки (что видно сразу, из их примера):** ФИО · Категория · Опыт работы · Опыт с агродронами · Обработано га · Работает на (модель) · Работал на · Собственный дрон · Дрон зарегистрирован · Бак-разбрасыватель · Прицеп · Услуги. → привести карточку прототипа к этому набору.

## 7. Законодательство и допуски РК (собрано из открытых источников, 2026-09-03)
Основной документ: **Правила использования БАС в воздушном пространстве РК** (приказ V2000022031, adilet.zan.kz). Регулятор — **CAA / Комитет гражданской авиации**.

**Категории операций с БАС** (по уровню риска):
- **«Открытая»** — до 1,5 кг без спец. условий; от 1,5 до 25 кг — при наличии у оператора **сертификата категории 1**.
- **«Специфическая»** — операции повышенного риска.
- **«Сертифицированная»** — самый жёсткий уровень; требуется **свидетельство внешнего пилота ДПАС** с квалификационными отметками от CAA.

**Сертификаты оператора БАС: категория 1 / 2 / 3** — это и есть I/II/III на схеме Нурлана. Точная детализация отличий категорий 1/2/3 — уточнить по тексту Правил при проектировании поля «допуск».
Обучение и выдача — через уполномоченные организации / CAA (caa.gov.kz/ru/obuchenie-bas). В профиле оператора: поле «категория допуска (1/2/3)» + «свидетельство внешнего пилота (да/нет, срок)» + статус верификации.

**Учёт/регистрация дронов** — ОТДЕЛЬНАЯ ветка, у Нурлана уже проектируется. НАШ модуль (операторы) её НЕ трогает. Справочно: учёту подлежат БВС от 250 г или с камерой/сенсорами.

**Закон РК «О персональных данных и их защите»**: согласие на сбор/обработку + отдельное согласие на маркетинг, право на удаление/хранение. Критично — база = ядро ценности проекта.
Самозанятость/налоги операторов — не наша зона на старте, пометка на будущее.

Все сёла КЗ (~6-7 тыс.) в фильтр не тащим — утонет UX. Схема:
- **Фильтр поиска — по областям** (20 регионов: 3 города респ. значения + 17 областей, актуально после реформы 2022), **мультивыбор** (1/несколько/все) — сделано, `frontend/src/regions.ts` + `RegionPicker`.
